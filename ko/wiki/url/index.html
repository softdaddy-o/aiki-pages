URL (웹 주소)

다른 이름: Uniform Resource Locator웹 주소URL 레코드

URL은 인터넷에 있는 자원 하나를 가리키는 주소야. WHATWG URL Standard는 URL을 scheme, host, port, path, query, fragment 같은 칸으로 이루어진 구조체로 정의해.

한 줄 정의

URL은 인터넷에 있는 자원 하나를 가리키는 주소야. 브라우저 주소창에 치는 https://... 문자열이 바로 그거거든. MDN 문서는 URL을 인터넷에 있는 고유한 자원의 주소라고 설명해. 브라우저가 URL을 읽는 규칙은 WHATWG가 관리하는 URL Standard에 적혀 있어. 편지 봉투 주소에 시, 구, 동, 번지 칸이 정해져 있듯이, URL도 정해진 칸에 정해진 값이 들어가.

구성요소와 작동

URL Standard는 URL을 ‘보편적 식별자를 나타내는 구조체(struct)‘로 정의해. 구조체는 이름 붙은 칸 여러 개를 하나로 묶은 데이터라고 보면 돼. 칸은 이렇게 생겼어.

  • scheme: 어떤 종류의 URL인지 나타내. https, mailto, file 같은 값이야.
  • username / password: 사용자 이름과 비밀번호. 보통은 비어 있어.
  • host: 자원이 있는 곳. 규격에 따르면 도메인(example.com), IP 주소(IPv4나 IPv6), 네트워크 주소로 해석하지 않는 불투명 호스트(opaque host), 빈 호스트 중 하나야.
  • port: 서버의 어느 문으로 들어갈지 정하는 번호. 비어 있을 수도 있어.
  • path: 서버 안에서 자원의 위치. /search처럼 생겼어.
  • query: ? 뒤에 붙는 추가 정보. 검색어 같은 게 들어가.
  • fragment: # 뒤에 붙는 값. 자원 안의 특정 위치를 가리켜.

규격은 scheme 가운데 여섯 개를 ‘특수 스킴’으로 따로 묶고, 각각 기본 포트를 정해 둬.

특수 스킴기본 포트
ftp21
file없음 (null)
http80
https443
ws80
wss443

https://example.com처럼 포트를 안 적어도 443으로 들어가는 이유가 이 표야. MDN 문서도 서버가 표준 포트(http 80, https 443)를 쓰면 보통 포트를 생략한다고 설명해. 거꾸로 서버가 다른 번호를 쓰면 :8000처럼 직접 적어야 하는 거지.

예시와 구분

규격에 실린 예시 https://localhost:8000/search?q=text#hello를 칸별로 나누면 이래.

칸값
schemehttps
hostlocalhost
port8000
pathsearch 한 칸
queryq=text
fragmenthello

username과 password는 비어 있어.

헷갈리기 쉬운 구분이 두 가지 있어. 하나는 URL, URI, IRI야. 셋을 따로 배운 적이 있을 텐데, URL Standard는 용어를 URL 하나로 통일했어. 규격은 URI와 IRI가 헷갈리기만 하고 실제로는 같은 알고리즘 하나로 처리한다는 이유를 들어.

다른 하나는 URL 문자열과 URL 레코드야. 주소창에 보이는 글자는 문자열이고, 그걸 읽어서 칸별로 나눠 담은 결과가 레코드야. 규격은 둘을 구분하려고 구조체를 ‘URL 레코드’라고도 불러.

코드에서도 이 구조를 그대로 쓸 수 있어. 규격은 URL을 해석하고 고치는 JavaScript URL 클래스와, query 칸을 다루는 URLSearchParams 클래스를 정의해.

const url = new URL("https://localhost:8000/search?q=text#hello");
url.port;                  // "8000"
url.searchParams.get("q"); // "text"

문자열을 직접 잘라서 칸을 찾는 대신 이 클래스로 꺼내면, 규격에 적힌 해석 규칙을 그대로 따르게 돼.

주의해서 볼 점

WHATWG 규격은 RFC 3986·3987을 지금 브라우저 구현에 맞추고, 그 과정에서 두 RFC를 대체하는 걸 목표로 밝혀. 이건 WHATWG가 스스로 적은 목표고, RFC를 관리하는 IETF 쪽 입장은 이번 근거 자료에 없어. 오래된 문서가 RFC 기준으로 URL을 설명해도 틀렸다고 단정할 건 없고, 브라우저 동작을 따질 때는 WHATWG 규격을 기준으로 보면 돼.

통과 원문 대조
주소창 URL을 칸별로 읽고 https 주소에 포트가 왜 안 보이는지 알고 싶은 독자 문제에 원문이 답하는지 보고, URL 정의·구성 칸·host 종류·JavaScript API 설명을 WHATWG URL Standard 원문 문장과 하나씩 맞춰 봤어.
  • 독자 문제: 주소창 URL을 칸별로 나눠 읽고 싶은 독자에게, 규격 4.1절의 칸 정의(scheme, host, port, path, query, fragment 등)로 답이 되는지 확인했어.
  • Reader problem: https 주소에 포트 번호가 왜 안 보이는지 묻는 독자에게, 규격 4.2절 기본 포트 표로 설명이 되는지 확인했어.
  • 규격이 URL을 '보편적 식별자를 나타내는 구조체(struct)'로 정의하고, 'URL 레코드'라는 이름도 쓴다는 문장을 원문에서 확인했어.
  • scheme, username, password, host, port, path, query, fragment 칸 이름을 4.1절 원문 표기 그대로 옮겼어.
  • host가 도메인, IP 주소, opaque host, 빈 호스트 중 하나라는 3.1절 문장과 본문 설명이 같은지 봤어.
  • URL 클래스와 URLSearchParams 클래스가 6장 API 절에 정의돼 있는지 확인했어.
통과 교차 검증 검증 출처 2
WHATWG 규격 원문과 MDN 학습 문서를 따로 놓고 URL 정의와 기본 포트가 서로 맞는지 확인했어.
  • 1차 출처 교차검증: URL 정의를 WHATWG 규격 원문과 MDN 문서에서 따로 확인했고, 둘 다 URL을 자원을 가리키는 주소·식별자로 설명해.
  • http 80, https 443 기본 포트를 규격 표와 MDN 설명 양쪽에서 대조했어.
  • JavaScript URL API가 규격의 목표 절과 6장 API 정의에 함께 나오는지 봤어.
통과 수치 검증
본문에 나온 기본 포트 숫자, 예시 포트 8000, RFC 번호를 원문 숫자와 맞춰 봤어.
  • ftp 21, http 80, https 443, ws 80, wss 443과 file의 기본 포트 없음(null)은 규격 4.2절 표 그대로야.
  • 예시 URL의 포트 8000은 규격 4.1절 표의 예시 입력 그대로 옮겼어.
  • RFC 3986, RFC 3987 번호는 규격 목표 절 문장 그대로야.
통과 비판 검토
WHATWG가 스스로 밝힌 목표를 확정된 사실처럼 쓰지 않았는지, 근거 자료 밖 내용이 섞이지 않았는지 다시 봤어.
  • RFC 3986·3987을 대체하겠다는 건 WHATWG 규격이 밝힌 목표라서 'WHATWG가 목표로 밝혀'로 적었고, IETF 쪽 입장은 근거 자료에 없다고 밝혔어.
  • URL·URI·IRI 용어 통일은 규격의 선택으로 적고, 모든 문서가 이 용어를 따른다고 단정하지 않았어.
  • 이번 입장 심사에서 허용된 주장 범위 밖이던 퍼센트 인코딩 상세 설명은 본문에서 뺐어.
  • RFC 폐기를 확정 사실처럼 읽힐 수 있는 표현은 WHATWG의 목표로 수정 완료.
  • 허용 범위 밖이던 퍼센트 인코딩 상세 설명은 삭제 완료.
